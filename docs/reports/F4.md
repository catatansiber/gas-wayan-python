# Laporan F4 - Review, Publish, dan Rekonsiliasi

Status: `READY_FOR_REVIEW`
Tanggal: 16 September 2026

Dijalankan dan diuji **di database dev/staging lokal saja** (PostgreSQL Docker Compose proyek
ini), sesuai instruksi eksplisit. Tidak ada migrasi produksi, tidak ada deployment, tidak ada
akun berbayar dibuat. Dokumen ini hanya berisi angka agregat - tidak ada nama pelanggan atau
nomor tabung individual yang dicetak di sini.

## Yang dibangun

- **Model baru** (`imports/models.py`): `PublishBatch` (satu eksekusi `publish_staging`),
  `SourceLink` (`StagingRow` <-> `Cycle` hasil publish, wajib per baris terpublish - A1),
  `ReviewDecision` (append-only: siapa, kapan, alasan - satu-satunya keputusan yang didukung F4
  adalah `EXCLUDE`). `StagingRow.publish_outcome` baru (`PENDING_REVIEW`/`PUBLISHED`/
  `EXCLUDED_APPROVED`) untuk rekonsiliasi wajib.
- **`imports/publisher.py`** - orkestrasi review+publish:
  - Kelompok = seluruh `StagingRow` dengan `serial_number_raw` sama (satu tabung), diurutkan
    kronologis (`sent_at`, fallback nomor baris sumber) - sesuai usulan B3.
  - **Publish atomic per kelompok**: satu kelompok = satu `transaction.atomic()`. Seluruh baris
    di kelompok itu dipublish sekaligus, atau tidak sama sekali. Kelompok lain tidak terpengaruh.
  - Kelompok hanya dipublish bila **seluruh** barisnya `review_status=READY` (F3: gas dikenal,
    tanggal kirim DAN kembali sama-sama terparse penuh) DAN tidak ada tumpang tindih kronologi.
    Baris/kelompok lain (termasuk yang sudah pernah `EXCLUDED_APPROVED`) tidak memblokir baris
    lain di luar kelompoknya.
  - **Kebijakan PENDING tetap memblokir**: gas kosong/tidak dikenal (B1), tanggal kembali
    kosong/hanya status tanpa tanggal (B2), dan konflik kronologi (B3 - termasuk duplikat
    bisnis, yang secara matematis selalu muncul sebagai tumpang tindih tanggal) semuanya
    membuat kelompok tetap `PENDING_REVIEW` - tidak pernah ditebak/dipaksa publish.
  - Mapping pelanggan: exact-normalized match ke `CustomerAlias` yang sudah ada (FR-03); bila
    tidak ada, `Customer` + alias baru dibuat. Ejaan mirip (bukan exact) TIDAK digabung otomatis.
  - Mapping tabung: `Cylinder.get_or_create` per `serial_number_raw`.
  - Publish memanggil `operations.services.dispatch_cylinder` lalu `return_cylinder` dengan
    `source="IMPORT"` dan idempotency key deterministik (`f4-dispatch-<staging_row_id>`) - audit,
    outbox, idempotency, dan constraint database F2 semuanya tetap berlaku tanpa jalur pintas.
  - Re-run aman (resume): baris `PUBLISHED`/`EXCLUDED_APPROVED` tidak diproses ulang.
- **Django Admin (layar review)** - `StagingRowAdmin`: kolom `publish_outcome`, filter/pencarian
  per tabung/pelanggan, **preview mapping** on-the-fly (pelanggan cocok/baru, tabung ada/baru,
  kode gas, layak publish - dihitung saat dibuka, TIDAK menulis apa pun), dan aksi
  **"Kecualikan dari publish (wajib alasan)"** dengan halaman konfirmasi (form alasan) yang
  memanggil `publisher.exclude_staging_row` (role ADMIN, alasan wajib, ditegakkan di server).
  `PublishBatch`/`SourceLink`/`ReviewDecision` read-only (`ReadOnlyAdminMixin`, konsisten F2/F3).
- **`python manage.py publish_staging --actor-username <user>`** - jalankan publish sungguhan
  (`--limit-serial` untuk membatasi ke tabung tertentu, dipakai demo/tes).
- **`python manage.py reconcile_report`** - rekonsiliasi `raw (non-blank) = PUBLISHED +
  PENDING_REVIEW + EXCLUDED_APPROVED`, dilaporkan **terpisah** dari pengecekan event IMPORT
  yatim (`LifecycleEvent.source=IMPORT` tanpa `SourceLink`). Menulis
  `docs/reports/f4-publish-summary.json` (agregat, aman untuk Git).
- `catalog.CustomerAlias.normalized_value` (field baru, migrasi `catalog/0002`) - indeks untuk
  exact-normalized match, diisi eksplisit oleh `imports/publisher.py` (bukan otomatis di
  `save()`, supaya `catalog` tidak bergantung ke `imports`).

## Hasil menjalankan publish terhadap staging sungguhan (F3, snapshot sama)

Dijalankan dua kali berturut-turut (`publish_staging`) lalu `reconcile_report`, terhadap 10.597
`StagingRow` hasil F3 di database dev:

| Metrik | Run 1 | Run 2 (re-run) |
| --- | ---: | ---: |
| Kelompok dilihat | 2.451 | 2.451 |
| Kelompok sudah selesai (skip, resume) | 0 | 48 |
| Kelompok dipublish | 48 | **0** |
| Kelompok diblokir | 2.403 | 2.403 |
| Baris dipublish | 56 | **0** |

Re-run kedua membuktikan idempotency: nol kelompok/baris baru, nol duplikat.

Rekonsiliasi (`reconcile_report`, lihat `docs/reports/f4-publish-summary.json`):

```text
raw_rows_total          : 11.137  (tetap sama dengan F3 - arsip raw tidak diubah publish)
blank_rows_total        : 540
staging_rows_total      : 10.597
PUBLISHED               : 56
PENDING_REVIEW          : 10.541
EXCLUDED_APPROVED       : 0
reconciliation_sum      : 10.597  == staging_rows_total -> COCOK
source_links_total      : 56      (1 SourceLink per StagingRow terpublish)
import_lifecycle_events : 112     (2 event per Cycle: DISPATCHED + RETURNED)
orphan_import_events    : 0       (semua event IMPORT tertelusuri lewat SourceLink)
```

**Interpretasi jumlah kecil yang berhasil publish (56 dari 10.597):** ini SESUAI DESAIN, bukan
bug. Kebijakan B1 (gas kosong/tidak dikenal, ~90% baris), B2 (tanggal kembali tanpa tanggal
pasti), dan B3 (konflik kronologi) semuanya masih `PENDING` - instruksi eksplisit sesi ini
("Kebijakan belum disahkan tetap memblokir data terkait") ditegakkan secara harfiah. 56 baris
yang publish adalah baris yang tidak bergantung pada satu pun kebijakan PENDING: gas resmi
dikenal, tanggal kirim DAN kembali sama-sama tanggal pasti terparse, dan tidak ada tabung lain
di riwayatnya yang mengaburkan urutan siklus. Begitu pemilik proyek mengonfirmasi B1/B2/B3
(lihat `docs/migration-decisions-pending.md`), jumlah yang layak publish akan naik signifikan
tanpa perlu mengubah kode `imports/publisher.py` - hanya perlu longgarkan syarat `review_status`
sesuai kebijakan yang dikonfirmasi (perubahan terpisah, menunggu keputusan pemilik).

## Tes yang dijalankan

`python manage.py test imports --settings=config.settings.test` -> **37/37 lulus** (25 F3 lama +
12 baru F4), data sintetis, mencakup persis skenario yang diminta:

- **Crash/resume**: `test_crash_mid_batch_then_resume` - simulasi proses mati setelah 1 dari 3
  kelompok independen selesai; kelompok pertama tetap commit (tidak ikut rollback), dua sisanya
  tetap `PENDING_REVIEW`; panggilan `run_publish` berikutnya melanjutkan tanpa duplikasi.
- **Re-run**: `test_rerun_after_publish_is_idempotent` - publish dua kali, kelompok kedua kali
  dilaporkan `already_resolved`, tidak ada `SourceLink`/`Cycle` duplikat.
- **Duplikat bisnis**: `test_business_duplicate_blocks_until_excluded` - dua baris sama
  persis (serial+tanggal kirim+tanggal kembali) otomatis terdeteksi sebagai tumpang tindih
  kronologi (bukan pengecekan terpisah - duplikat murni selalu muncul sebagai overlap), kelompok
  diblokir; setelah Admin mengecualikan satu baris beralasan, baris sisanya berhasil publish
  di run berikutnya.
- **Rollback batch/kelompok**: `test_group_rolls_back_completely_on_mid_group_failure` - error
  disuntik di tengah kelompok 2-baris (lewat `unittest.mock.patch` pada `return_cylinder`);
  KEDUA baris di kelompok itu tetap `PENDING_REVIEW`, nol `SourceLink`/`Cycle`/`Cylinder`
  tercipta untuk kelompok itu, sementara kelompok independen lain yang sudah commit sebelumnya
  tidak terpengaruh.
- **Rekonsiliasi**: `test_reconciliation_raw_equals_published_plus_pending_plus_excluded` -
  raw staging = published+pending+excluded persis, untuk campuran ketiga outcome.
- Kebijakan PENDING memblokir: `test_group_blocked_when_any_row_not_ready`,
  `test_pending_gas_policy_blocks_group`.
- Arsip raw tetap dapat dicari setelah publish: `test_raw_archive_remains_searchable_after_publish`.
- Role: `test_role_enforcement_on_publish_and_exclude` (VIEWER tidak bisa publish, OPERATOR
  tidak bisa exclude, alasan kosong ditolak), `test_cannot_exclude_already_published_row`.
- Mapping alias exact-normalized: `test_customer_alias_exact_normalized_reused_across_rows`.

`python manage.py test --settings=config.settings.test` (seluruh proyek) -> **88/88 lulus** (51
F1+F2 + 25 F3 + 12 F4), tidak ada regresi. `ruff check .`/`ruff format --check .` bersih.
`makemigrations --check --dry-run` -> tidak ada drift.

**Dijalankan sungguhan di staging (bukan hanya tes otomatis)**: dua kali `publish_staging` +
satu kali `reconcile_report` terhadap 10.597 `StagingRow` nyata hasil F3 - lihat tabel di atas.

## Yang TIDAK dijalankan / TIDAK dalam scope F4

- Tidak ada migrasi/publish ke lingkungan produksi - seluruhnya di database dev/staging lokal
  (`docker-compose.yml` proyek ini).
- Tidak ada "pembatalan" (undo) batch yang SUDAH commit - hanya rollback OTOMATIS saat error di
  tengah kelompok (diuji, lihat di atas). Undo retroaktif setelah commit butuh reversal untuk
  event `RETURNED`, yang statusnya masih `PENDING` (MIG-P09) - sengaja tidak ditebak di sini.
  `exclude_staging_row` menolak baris yang sudah `PUBLISHED` (lihat
  `test_cannot_exclude_already_published_row`).
- Merge alias untuk ejaan MIRIP (bukan exact) tetap manual/di luar scope otomatis F4 - hanya
  exact-normalized yang digabung otomatis (FR-03, konsisten `docs/column-mapping.md`).
- Tidak ada layar publish/preview berbasis template HTML terpisah - "layar review Admin" F4
  memakai Django Admin (konsisten ADR-P002: "Django Admin dapat dipakai untuk pengelolaan
  awal"), bukan UI operasional baru (itu F5).

## Risiko dan item terbuka

- MIG-B01/B03 (gas 665 baris tidak dikenal) dan kebijakan B1/B2/B3 tetap `PENDING` - mayoritas
  data (10.541 baris) tertahan `PENDING_REVIEW` sampai dikonfirmasi. Ini **diharapkan**, bukan
  kegagalan sistem.
- MIG-P09 (reversal RETURNED/EXCHANGED) masih memblokir kemampuan "undo publish setelah commit".
- 2.403 kelompok diblokir - sebagian besar karena satu baris bermasalah dalam riwayat satu
  tabung memblokir SELURUH riwayat tabung itu (bukan hanya baris bermasalahnya) sesuai usulan
  B3. Ini konsisten dengan instruksi, tapi berarti dampak satu baris buruk bisa lebih luas dari
  yang terlihat sekilas - perlu dikomunikasikan ke Admin yang mereview.

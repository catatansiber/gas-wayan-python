## 2. Concurrency PostgreSQL (3-5 pengguna bersamaan)

Dua lapis bukti, keduanya PostgreSQL nyata (`TransactionTestCase`, thread sungguhan, bukan
simulasi):

- **Layer service** (F2, `operations.tests.ConcurrencyTests`/`ExchangeConcurrencyTests`) - dua
  dispatch bersamaan pada tabung sama (tepat satu berhasil), dua exchange arah berlawanan (tidak
  deadlock).
- **Layer web (baru F7)**, `operations.test_concurrency_web.WebConcurrencyTests` - **5 Operator
  berbeda** mem-POST form kirim untuk tabung YANG SAMA hampir bersamaan lewat Django test Client
  (request HTTP sungguhan, bukan panggilan Python langsung):
  - `test_n_users_dispatch_same_cylinder_only_one_succeeds` - tepat 1 redirect sukses (302), 4
    lainnya kembali ke form dengan error (200), tepat 1 `Cycle` tersimpan.
  - `test_n_users_double_click_same_request_only_one_cycle` - 5 thread mem-POST payload+
    idempotency key **identik** bersamaan (simulasi retry jaringan/double-click ekstrem) -
    seluruhnya redirect sukses (idempotency replay), tetap hanya 1 `Cycle`.

Kedua tes lulus konsisten (dijalankan berulang, tidak flaky).

## 3. Keamanan

Diperiksa dengan `python manage.py check --deploy --settings=config.settings.prod` (checklist
resmi Django) plus tinjauan manual kode:

| Item | Status sebelum sesi ini | Tindakan F7 |
| --- | --- | --- |
| `DEBUG=False` di produksi | Sudah (`config/settings/prod.py`, hardcoded, tidak dari env) | Diverifikasi ulang, tidak berubah |
| HTTPS/redirect | `SECURE_SSL_REDIRECT=True` default | Diverifikasi ulang, tidak berubah |
| Cookie aman | `SESSION_COOKIE_SECURE`/`CSRF_COOKIE_SECURE=True` | Diverifikasi ulang, tidak berubah |
| CSRF | `CsrfViewMiddleware` aktif, seluruh form pakai `{% csrf_token %}` | Diverifikasi ulang (grep seluruh template), tidak berubah |
| HSTS | **Belum diset** (`check --deploy` -> `security.W004`) | **Ditambahkan** `SECURE_HSTS_SECONDS` (default 1 tahun) + `INCLUDE_SUBDOMAINS`. `SECURE_HSTS_PRELOAD` SENGAJA tetap `False` (submit ke preload list browser tidak bisa dibatalkan - butuh keputusan eksplisit pemilik proyek, bukan default otomatis) |
| Rate limiting | **Tidak ada** | **Ditambahkan** `identity/throttle.py` - 5 percobaan login gagal per (IP, username) per 5 menit, lewat Django cache framework (LocMemCache, proses tunggal - cukup untuk deployment satu proses; Redis/cache bersama menyusul bila multi-proses, lihat MIG-P01) |
| Role server-side | Sudah (`role_required`, F1-F5) | Diverifikasi ulang lewat UAT matrix, tidak berubah |
| Log tanpa data sensitif | Tidak ada `LOGGING` custom; tidak ada kode aplikasi yang mencatat `request.POST`/password (diverifikasi lewat pencarian kode) | Tidak ada tindakan - tidak ada yang perlu dihapus |
| `X-Content-Type-Options`, `X-Frame-Options` | Sudah (`SecurityMiddleware`/`XFrameOptionsMiddleware` bawaan, aktif sejak F1) | Diverifikasi ulang, tidak berubah |

Setelah perbaikan HSTS, `check --deploy` hanya menyisakan satu WARNING (`security.W021`,
"SECURE_HSTS_PRELOAD belum True") - **keputusan sengaja**, dijelaskan di tabel, bukan celah.

## 4. Pemulihan backup (drill sungguhan, database staging lokal)

Dijalankan lewat `docker exec` terhadap container Postgres proyek ini (`gas-wayan-python-
postgres-1`), **bukan simulasi**:

1. `pg_dump -F c` database `gaswayan_dev` -> file dump 1,5 MB.
2. Buat database baru `gaswayan_restore_test` di instance Postgres yang sama.
3. `pg_restore` dump ke database baru - **tidak ada error**.
4. Bandingkan jumlah baris 7 tabel kunci antara `gaswayan_dev` (asli) dan
   `gaswayan_restore_test` (hasil restore):

   | Tabel | Asli | Hasil restore |
   | --- | ---: | ---: |
   | `catalog_customer` | 48 | 48 |
   | `catalog_cylinder` | 48 | 48 |
   | `imports_rawrow` | 11.137 | 11.137 |
   | `imports_stagingrow` | 10.597 | 10.597 |
   | `imports_sourcelink` | 56 | 56 |
   | `operations_cycle` | 56 | 56 |
   | `operations_lifecycleevent` | 112 | 112 |

   **Cocok persis di seluruh tabel.**
5. Database `gaswayan_restore_test` dan file dump lokal dihapus setelah drill selesai (dump
   sempat berisi data pelanggan asli hasil publish F4 - tidak disimpan, tidak masuk Git).

**Keterbatasan drill ini:** dilakukan di instance Postgres yang sama (bukan mesin/lingkungan
terpisah) - cukup untuk membuktikan mekanisme `pg_dump`/`pg_restore` bekerja dan data konsisten,
TAPI belum membuktikan pemulihan di infrastruktur produksi sungguhan (target VPS/managed masih
MIG-P04 `PENDING`). Rehearsal lintas-mesin perlu diulang saat F8.

## 5. Performa (data sintetis, TIDAK mengklaim kapasitas produksi)

Dibangun 3.000 `Cylinder`, 300 `Customer`, 20.000 `Cycle` (40.000 `LifecycleEvent`) sintetis di
database dev lewat `python manage.py perf_benchmark` (bulk insert, data dihapus otomatis
setelah selesai - diverifikasi 0 baris tersisa). 30 sampel per pengukuran, in-process (Django
test Client dalam proses yang sama - **bukan** latency jaringan/browser sungguhan):

| Operasi | p50 | p95 | Catatan |
| --- | ---: | ---: | --- |
| Cari nomor tabung (exact) | 5,7 ms | 9,4 ms | Terindeks (`unique`) |
| Cari/daftar per nama pelanggan | 27,8 ms | 38,9 ms | Join + `icontains`, tidak terindeks - masih jauh di bawah target |
| Log penggunaan (listing global) | 8,4 ms | 13,6 ms | |
| Detail/riwayat tabung | 8,7 ms | 11,4 ms | |
| Mutasi kirim+kembali (2 operasi) | 17,5 ms | 23,8 ms | Lewat `operations.services` langsung |

Hasil lengkap: `docs/reports/f7-performance.json`.

**Interpretasi wajib (jangan disalahartikan):**
- Target lama (p95 cari <=1 detik, command <=2 detik, requirements.md MIG-N01/N02) **belum
  disahkan** - angka di atas dicatat sebagai referensi pengukuran, BUKAN bukti kelulusan target
  resmi (butuh verifikasi pemilik di lingkungan mendekati produksi, bukan laptop dev).
  Namun demikian, seluruh angka di atas jauh di bawah ambang tersebut pada volume yang diuji.
- 20.000 `Cycle` sintetis **BUKAN** bukti mampu menangani kebutuhan lama 5 juta event/5 tahun -
  itu ~250x lebih besar dari volume yang diuji di sini. **Tidak ada klaim kapasitas 5 juta
  dibuat** dari hasil ini.
- Timing in-process tidak mencakup latency jaringan nyata, TLS, atau beban browser - hanya
  representatif untuk biaya query+render di server.
- Karena seluruh angka jauh di bawah target (bahkan operasi paling lambat, cari-per-pelanggan,
  <40ms vs target 1000ms), **belum ada index/cache baru ditambahkan** - konsisten prinsip F7
  "ukur sebelum menambah cache atau partisi". Bila volume data sungguhan bertambah signifikan
  (pasca F4 lanjutan mempublish lebih banyak), ukur ulang sebelum memutuskan optimasi.
